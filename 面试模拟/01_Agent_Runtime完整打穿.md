## 0. 简历原文（本条唯一范围）

> **Agent 编排与执行治理：**参与多平台商品搜索链路重构，将适合独立执行的平台级检索任务从 Main Agent 中拆分为按需 Fork 的 SubAgent，负责子任务 dispatch、独立执行上下文、结果回传及异常处理；补充迭代上限、执行超时与循环终止机制，并通过异步 fan-out 并发执行多平台搜索，平均搜索链路耗时降低 **[待实测]%**。

拆成三句，后面全文只回答这三句：

| 简历在说什么 | 对应本文 |
|---|---|
| **为什么做 / 解决什么** | 多平台搜索挤在 Main 里：慢、主上下文脏、难治理 |
| **我做了什么** | Fork SubAgent；dispatch / 独立上下文 / 回传 / 异常；迭代上限·超时·循环终止；fan-out 并发 |
| **产出** | 搜索链路耗时降 `[待实测]%`（用实验填） |

角色语气：**参与重构与落地**，不是「独立造了整个购物 Agent」。

## 1. 为什么需要它（为什么做）

项目简介写的是跨境购物 Agent 的 **V1→V2 工程优化**，你在第一条上的切入点是：**多平台商品搜索这条执行链路**。

用户一句需求往往要查多个平台。搜索任务有三个特点：

1. 各平台彼此独立，适合并行；  
2. 单平台检索过程长、中间结果大；  
3. 单平台内部还可能多轮工具调用。

如果这些都压在 Main Agent 一条链上执行，编排层就会同时承受延迟、上下文和可控性压力——所以要做「编排与执行治理」，而不是只调一个搜索函数。

---

## 2. 原来的系统有什么问题（解决了什么）

**V1（重构前）典型形态：**

```text
Main Agent 串行：
  搜平台A → 大段结果进主上下文
  → 搜平台B → 再灌进主上下文
  → …
  → 再往后做合流/决策
```

| 问题 | 具体表现 | 和你工作的关系 |
|---|---|---|
| 搜索链路慢 | 多平台串行，耗时近似相加 | 要用 fan-out 并发降墙钟时间 |
| 主上下文被检索污染 | 各平台中间结果堆进 Main | 要拆到 SubAgent，主线只收最终回传 |
| 执行难治理 | 死循环刷工具、卡死、递归派活 | 要补迭代上限、超时、循环终止等机制 |

**解决目标（对齐简历动词）：**  
把「适合独立执行的平台级检索」从 Main 拆出去 → 按需 Fork SubAgent → 管好 dispatch / 上下文 / 回传 / 异常 → 加上限与并发 → **搜索链路更快、主执行更稳**。

## 3. 我做了什么（对照简历逐项）

下面每项都是简历里的原词，后面是机制含义（面试就按这个粒度讲）。

### 3.1 平台级检索：Main → 按需 Fork SubAgent

- **做了什么**：识别「一个平台上的检索」适合独立跑，从 Main 拆成 SubAgent。  
- **按需**：不是每个工具都 Fork；平台检索才拆，合流类计算仍留在 Main（见数据流）。  
- **SubAgent 同质**：与 Main 同一套模型 / Prompt / 工具集，换独立执行上下文，不是另养一个「搜索专家 Agent」。

### 3.2 子任务 dispatch

- **做了什么**：提供/落地 `dispatch_tool`（或等价派发入口）：Main 传入子任务描述 `demands`，拉起一个 SubAgent 跑完。  
- **落点**：`生产级架构全景/app/agent/dispatch_tool.py`。

### 3.3 独立执行上下文

- **做了什么**：每个 SubAgent 使用独立 `thread_id` + Checkpointer，检索中间过程不进 Main 的 messages。  
- **落点**：`main_agent.py`（共享 `build_agent` + 按 `thread_id` 分桶）、`dispatch_tool.py`（生成 `sub-…` thread）。

### 3.4 结果回传

- **做了什么**：SubAgent 结束后只把**最终结果字符串**作为 Observation 回给 Main，不回灌整段子对话。  
- **为何重要**：这直接对应「解决主上下文被中间检索污染」。

### 3.5 异常处理

- **做了什么**：Fork 超限、子任务失败等转为**可读拒绝/错误信息**回到 Main，让主链路可换策略，而不是把整个 run 直接打崩。  
- **落点**：`fork_guard.py`（深度上限）+ `dispatch_tool` 捕获后返回拒绝串。

### 3.6 迭代上限、执行超时、循环终止

| 机制 | 解决什么 | 落点 |
|---|---|---|
| 迭代上限 | Main/Sub 不收敛、空转 | `main_agent` 主 `recursion_limit`；子更小上限 |
| 执行超时 | 某步卡死不返回（与「轮次用尽」不同） | 目标形态：`wait_for(ainvoke)`；见 `02_同步_并发_异步定稿.md` + `demo_timeout_guard.py` |
| 循环终止 | 反复刷同一工具 / 超长结果拖死上下文 | `middleware.py`（调用次数限制、结果截断）；亦可配合 LoopDetector 叙事 |

简历写的是「补充」这些机制——面试强调：**编排拆开之后必须加刹车，否则 Fork 会放大失控面**。

### 3.7 异步 fan-out 并发多平台搜索

- **做了什么**：多平台检索时，让 Main 同轮发出多路 dispatch，运行时并发执行（fan-out），墙钟接近最慢一路，而不是各平台耗时之和。  
- **说清边界**：  
  - 简历里的「异步 fan-out」= **多路子任务并发推进**（降搜索链路耗时）；  
  - 不等于「我把公司整个后端改成 asyncio」。全链路 async 是项目目标形态，本条数字来自**并发搜索**，见定稿文档。

### 3.8 产出：平均搜索链路耗时降低 `[待实测]%`

- 简历数字未填死：要用 §9 实验自己测、自己填。  
- 测法口径：固定多平台 query，对比「串行派发」vs「同轮 fan-out」，算 `(串行−并行)/串行`。

## 4. 它到底怎么工作（串起来）

```text
Main Agent 判断：这是可独立的平台级检索
  → dispatch(demands)  × N（可同轮 fan-out）
       → 进入 SubAgent（独立 thread_id）
       → 子侧自己多轮检索/决策
       → 回传最终 str（或异常/拒绝说明）
  → Main 用回传结果继续后续步骤
全程受：迭代上限 / 超时 / 循环终止 约束
```

**一句话：**你做的是把平台搜索从 Main 的「内联执行」改成「可派发、可隔离、可回传、可刹住、可并发」的执行治理。

## 5. 数据怎么流（要能自己画）

```text
User 购物需求
  → Main Agent（主 thread_id）
       │
       ├─ 判定：平台级检索 → 需要 Fork
       │
       └─ fan-out：
            dispatch(平台A) ──► SubA（独立上下文）──► 回传结果A ─┐
            dispatch(平台B) ──► SubB（独立上下文）──► 回传结果B ─┼─► Main 合流
            dispatch(平台C) ──► SubC …                         ─┘
       │
       →（后续合流/决策仍在 Main，不在本条展开成检索算法）
```

你必须能指着图回答：

- **谁调用谁**：Main 调 dispatch，Sub 调具体检索工具。  
- **输入**：`demands`（子任务描述）。  
- **输出**：最终结果字符串 / 拒绝说明。  
- **State 在哪**：主、子各一份 messages，靠 `thread_id` 分开。  
- **并发在哪**：同轮多个 dispatch，不是一个 dispatch 里写死四平台循环。  
- **出错谁处理**：护栏与 dispatch 把异常变成可观察回传，Main 决定降级或改派。

## 6. 各模块分别负责什么（输入 / 输出）

只列与本条简历动词相关的模块：

| 模块（全景） | 输入 | 输出 | 对应简历 |
|---|---|---|---|
| `dispatch_tool` | `demands: str` | 子最终 `str` 或拒绝串 | dispatch、回传、异常 |
| `fork_guard` | 进入/退出一层 fork | 允许或超限异常 | 异常处理（深度） |
| `main_agent` | `query` + 主 `thread_id` | 主链路最终回复 | 组装入口、迭代上限 |
| `middleware` | 工具调用前后 | 截断后的结果 / 拦超额调用 | 循环终止 |
| `tool_registry` | — | Main/Sub 同一 `FULL_TOOL_SET` | 同质 SubAgent 的前提 |
| `prompts` | 系统策略文本 | 模型何时 dispatch、如何写 demands | 行为约束（配合代码） |

## 7. 最小实现（能写到这个契约即可）

```text
# 派发
dispatch(demands):
  if fork_depth >= MAX: return "拒绝：超过 fork 深度"
  sub_thread = new_id()
  result = same_agent.invoke(demands, thread_id=sub_thread, max_iters=子上限)
  return str(result.final)

# 主入口
run(query, main_thread):
  agent.invoke(query, thread_id=main_thread, max_iters=主上限)
  # 多平台：由模型同轮多次调用 dispatch → 运行时 fan-out
```

**关键代码为什么这样写（掌握标准）：**

| 写法 | 原因 |
|---|---|
| Main/Sub 共用同一 `build_agent` | 同质；隔离靠 `thread_id` 不是靠两套 Agent 类 |
| 回传只要最终 str | 防止子中间过程污染 Main——这是本条要解决的核心问题之一 |
| 超限返回字符串而不是抛穿 | 异常处理要让 Main 还能继续决策 |
| 并发不在单个 dispatch 内写 for-平台 | 简历的 fan-out 是「多路派发并发」，职责在编排层 |

## 8. 为什么选择这个方案

1. **问题匹配**：要解决的是平台检索的隔离 + 并行 + 可控，不是重做业务搜索算法。  
2. **同质 Fork**：平台检索彼此同型，一份 Prompt/工具即可，维护成本低。  
3. **治理可叠加**：拆开之后才能干净地加迭代上限、超时、循环终止。  
4. **收益可测**：fan-out 对搜索链路耗时有直接、可实验的影响（`[待实测]%`）。

## 9. 替代方案与 trade-off

| 替代 | 能解决什么 | 相对你方案的代价 |
|---|---|---|
| Main 内直接并发调多个 `item_search` | 也能降延迟 | **独立执行上下文弱**：中间结果仍易进 Main；子侧难自己多轮 |
| 异构 SearchAgent / 多专家 | 边界看起来清晰 | 多 Prompt/工具维护；与「同型平台检索」不匹配，超出本条必要复杂度 |

**当前方案 trade-off（主动讲）：**

- 回传是字符串 → 合流是否稳，依赖子任务输出约束（Prompt/格式），不是强类型保证。  
- fan-out 依赖 Main「同轮发出多路 dispatch」→ 要靠策略与轨迹验收，不是 Python 里写死四路。  
- 超时「真取消」依赖异步调用链；若仍是同步 invoke，可能出现「调用方不等了但后台还在跑」——实验见 timeout demo。

## 10. 怎么做实验验证（填 `[待实测]`）

实验只服务简历这句：**平均搜索链路耗时降低 [待实测]%**，外加证明护栏有用。

### 10.1 耗时（必做）

```bash
python3 生产级架构全景/demos/demo_parallel_fork.py
```

记录串行 / 并行墙钟，计算：

```text
降低比例 = (串行耗时 − 并行耗时) / 串行耗时
```

把该比例填进简历；面试说明：固定多平台、I/O 等待为主；限流严重时比例会下降。

### 10.2 超时与「假取消」（配合「执行超时」）

```bash
python3 生产级架构全景/demos/demo_timeout_guard.py
```

能讲清：你要的治理是「超时后任务停」，而不是只停等待。

### 10.3 异常与循环（轨迹级）

准备少量固定 query，检查：

- 超深 fork 是否回传拒绝而非崩溃；  
- 是否出现同工具空转被限制；  
- 超长 Tool Result 是否被截断，避免拖死 Main。
