## 1. 这个项目是什么

**一句话（原文第 09 章）**：Globex 是跨平台对话式购物 Agent，不是搜索框。围绕复杂购物目标，做需求拆解、跨平台并行检索、比价、关税/运费、偏好记忆、过程可视化，最后给出购买清单。

**架构一句话**：

```text
1 个主 AgentLoop
+ 按需 fork 的 N 个同质子 AgentLoop
+ 9 个业务 Agent Tool + 1 个 dispatch_tool（fork 元工具）
+ 5 类基础设施（三塔召回 / Cache Breakpoint / 长期记忆 / AGUI / 评测训练）
+ HTTP 启任务 + WebSocket 推进度
```

**典型用户 query**：

> 我想买一套便宜又抗造的旅行三件套，预算 300，不要塑料，喜欢小众一点。

系统要像「购物研究员」：先理解约束，再跨 Amazon / Shopee / AliExpress / eBay 查，再比到手价、按偏好精挑，最后给清单和理由。

## 2. 端到端链条（先背这条）

```text
用户输入（自然语言 / 可选上传截图）
  → FastAPI 创建任务，立即返回 thread_id
  → WebSocket 按 thread_id 推 AGUI 事件（过程可见）
  → 主 AgentLoop 启动（独立 checkpoint / 对话 State）
      →（可选）读长期记忆 Store，注入 system prompt
      → Think：信息够不够？要不要 fork？
      → Planner：拆预算 / 品类 / 材质 / 风格 / 平台约束
      → CategoryInsight：品类常识 / 爆款要点（RAG）
      → 跨平台：一次 Think 发出多个 dispatch_tool
            → 同质子 Agent × N（独立 thread_id）
            → 各子 Agent 内调 ItemSearch（一平台一次）
            → 只把压缩后的字符串结果回主 Agent
      → 主 Agent 合流候选
      → PriceCompare（币种归一比价）  —— 不 fork
      → ShippingCalc（运费/关税/到手价）—— 不 fork
      → ItemPicker（硬约束过滤 + 软偏好精挑）
      → ShoppingSummary（终结出口，之后应停止检索）
  → 偏好 Reflect 写回 Store（跨会话）
  → 轨迹进 trace_logger → 评测 / 训练飞轮
```

记住三条硬规则：

1. **工具选择由 LLM 在运行时决定**，不是 Python 写死的 workflow（否则只是套了 LLM 壳的流水线）。  
2. **PriceCompare / ShippingCalc 是确定性合流计算，不 fork**。  
3. **ShoppingSummary 是收敛出口**：调用后不应再开检索类工具。

## 3. Agent 架构怎么运行

### 3.1 主 AgentLoop 是什么

主 loop 不是路由器，是**完整决策者**：同一套 LLM、同一份 system prompt、同一份 `FULL_TOOL_SET`。每轮大致是：

```text
Think（看 State / Observation）
  → 选工具或直接回复
  → Act（调工具 / dispatch_tool）
  → Observe（把工具结果写回 messages）
  → 再 Think……直到 Summary 或超时/轮次上限
```

框架侧（LangGraph / `create_agent`）：State 主要是 `messages`；用 `thread_id` + Checkpointer 隔离会话；`recursion_limit`（主 30）防不收敛；主任务 300s 超时在**第3档目标形态**下用 `asyncio.wait_for` + `ainvoke`（见 `02_同步_并发_异步定稿.md`）。

### 3.2 同质子 Agent 是什么

子 Agent **不是**「搜索专用机器人」这类异构角色，而是主 Agent 的**同质克隆**：

| | 主 Agent | 子 Agent |
|---|---|---|
| LLM / Prompt / 工具集 | 相同 | 相同（含 `dispatch_tool`，靠深度护栏限制） |
| `thread_id` | 用户会话 | `sub-{uuid}-d{depth}` |
| 输入 | 用户 query | 主 Agent 写的 `demands` 字符串 |
| 输出去向 | 前端 / 任务结果 | 作为 `dispatch_tool` 的字符串 Observation 回主 Agent |

fork 的三个判断（满足其一即可考虑）：能并行 / 需上下文隔离 / 子链路深。

### 3.3 并行到底怎么发生（简历①）

主 Agent **一轮 Think** 里对多平台各发一个 `dispatch_tool` → 同一条 AIMessage 多个 `tool_calls` → 框架用线程池并发执行 → 总耗时≈最慢一路，而不是各路之和。这是「并行降延迟」的技术故事；量级上可对应简历约 65%。

### 3.4 防失控（保证「跑得完」）

| 风险 | 手段 | 原文 |
|---|---|---|
| 无限递归 fork | fork 深度上限（如 2） | 第 14 章 |
| 工具死循环 | 同工具调用次数限制 | 第 14 章 |
| 单次结果撑爆上下文 | 工具结果截断 | 第 14 章 |
| 任务卡死 | 主/子超时 | 第 14 章 |
| 长对话 token / 缓存冲突 | Cache Breakpoint | 第 05 章 |

## 4. 九个业务工具：干什么、谁调、怎么联动

> `dispatch_tool` 不算第九个业务工具；它是 fork 元工具。

| 工具 | 干什么 | 常见谁调 | 上游吃什么 | 下游吐给谁 |
|---|---|---|---|---|
| **Planner** | 自然语言 → 结构化购物需求 | 主 | 用户 query | 后续所有决策的「约束清单」 |
| **ChatFallback** | 闲聊 / 进不了购物链 | 主 | 非购物意图 | 结束或澄清 |
| **WebSearch** | 外部评测、趋势、攻略 | 主/子 | 品类或品牌疑问 | 调整搜索词 / 兜底判断 |
| **CategoryInsight** | 品类常识、爆款、选购要点（RAG） | 主/子 | 品类名 / 场景 | 增强 ItemSearch query |
| **ItemSearch** | **商品数据入口**；一次一平台 | 主/子（多平台靠 fork） | query + platform + 可选用户 | Candidate 列表 |
| **PriceCompare** | 多币种归一、比价排序 | 主 | Candidate[] | PricePoint / ranked |
| **ShippingCalc** | 运费、关税、到手价 | 主（也可子） | 价格候选 | LandedCost[] |
| **ItemPicker** | 硬过滤 + 软偏好精挑 | 主 | LandedCost + 偏好/黑名单 | 1–3 件 PickedItem |
| **ShoppingSummary** | 最终清单 + 理由；**终结** | 主 | 精选结果 | 用户可见答案 |

### 4.1 数据合同（单向流，不要倒着补）

```text
PlannerOutput / ShoppingRequirements
  → CategoryInsightOutput（常识，不直接是商品）
  → ItemSearchOutput / Candidate[]
  → PriceCompareOutput / PricePoint[]
  → ShippingCalcOutput / LandedCost[]
  → ItemPickerOutput / PickedItem[]
  → ShoppingSummaryOutput
```

原则（原文复刻方案与第 11/12 章一致）：

- 下游需要的字段由上游透传或明确默认值。  
- **禁止** ShippingCalc 再回头调 ItemSearch 补字段。  
- 跨平台同款用 `same_group_id` 关联，**不要合并成一条**（否则没法比价）。

### 4.2 一条「旅行三件套」联动示例（理想路径，非强制顺序）

```text
Planner
  → CategoryInsight（收纳/材质避坑）
  → dispatch_tool ×4（amazon/shopee/aliexpress/ebay 各搜）
       各子 Agent：ItemSearch
  → PriceCompare
  → ShippingCalc
  → ItemPicker（不要塑料、预算 300）
  → ShoppingSummary
```

中途可自适应（原文第 03-1 强调这才是 Agent 而非固定 workflow）：

- 某平台塑料款过多 → 再调 CategoryInsight / 改搜索词  
- 杂牌多 → WebSearch 找口碑  
- 全超预算 → 反思预算或品类，而不是硬出清单

## 5. 五类基础设施在链条里的位置

| 基础设施 | 挂在哪 | 作用 |
|---|---|---|
| **三塔向量召回** | `ItemSearch` 内部 | Query/User/Item 编码 + ANN，决定候选上限 |
| **Cache Breakpoint** | 主 loop 每步后/长对话 | 断点前保 Prompt Cache，断点后可压缩 |
| **长期记忆 Store** | 会话开始注入 / Reflect 写回 | 「不要塑料」跨会话生效 |
| **AGUI** | Monitor → WebSocket | 前端看见 tool/fork/结果 |
| **评测训练闭环** | 离线 + 轨迹回流 | Rubric/Judge → SFT / Agentic RL |

Agent Tool vs 普通 Python 能力：

- 模型能直接调的：九工具 + `dispatch_tool`  
- 模型看不到、工具内部调用的：`fx` / `duty` / `shipping` 规则、`towers` / `ann`、Store 读写、压缩器

## 7. 怎么评估、怎么保证效果好

### 7.1 评测体系（原文第 08 章）——质量命门

没有 Rubric 就没有稳定 reward，只能靠改 Prompt 打地鼠。

**P0（一票否决）**：违禁品、远超预算、泄露内部 ID/工具名、人群场景冲突……  
**P1（规范扣分）**：缺 Summary、该有的工具链缺失、死循环、同工具刷太多次……  
**P2（质量加分）**：覆盖隐式需求、组合策略、材质/场景专业度……

自动化流程（原文）：

```text
query → 强模型生成该 query 的 Rubric
     → Agent 跑出 answer + trace
     → Judge 按 Rubric 打分
     → 高分轨迹进 SFT；分数进 Agentic RL reward
```

原文称自动评分与资深运营一致性可达约 90%+——面试时当作「方案目标/文档数字」，说明口径是 Judge↔人工对齐，不是你个人拍的。

### 7.2 召回侧评测（原文第 04-2 / 13-1 章）

| 指标 | 用途 |
|---|---|
| Recall@K / MRR / NDCG | 三塔与 RAG 是否在变好 |
| 空召回率、P50/P99 延迟 | 线上可用性 |
| Cache 命中（召回 query cache / Prompt Cache 分清） | 成本与延迟 |

发版叙事：召回指标跌破阈值 → 不发版或回滚索引/模型版本。

### 7.3 「效果好」靠的是一整条飞轮，不是单点 Prompt

```text
好的商品底座（合规采买 + 同构 + 质量分级）
  → 召回准（三塔 + Hybrid + Rerank）
  → Agent 决策稳（防失控 + 压缩 + 记忆）
  → 轨迹可评（Rubric/Judge）
  → 高分轨迹训练（SFT → Agentic RL）
  → 线上 trace 回流 ADS → 再指导采买与 fork 策略
```

运行时保底（第 14 / 13-1）：

- 防失控四件套  
- 组件降级（OpenSearch/Reranker/Tower 挂了仍返回低置信结构）  
- 次生产级再加：`ops` 开关与回滚（讲解层）

### 7.4 和简历数字的关系（诚实口径）

| 简历数字 | 地图里对应哪一层 | 原文支撑 |
|---|---|---|
| 30 轮 / 300s | 防失控 | 第 14 章有精确常量 |
| 并行降延迟 ~65% | fork 并发 I/O | 量级可辩护；应用固定 query 压测讲 |
| Cache 命中 ~80% | Cache Breakpoint | 第 05 章有 15%→80%+ |
| 记忆命中 72% | Store 读取/注入 | **原文未找到该数字**，需自拟可辩护口径 |
| 召回 +22% / 跨语言 +35% | 三塔 vs Query-only / 跨语言子集 | **原文无对比表**；定稿见 `文档/简历第四条_三塔向量召回/01` §5 |

## 8. 数据从哪里来（自圆其说 + 真实依据）

### 8.1 原文怎么定的（必须先说这句）

**第 09-1 章原话级结论**：

> 商品数据**不靠自建爬虫**，也**不直接接四个平台官方 API**，而是从**外部合规数据提供商采买**。项目要做的是把 Amazon / Shopee / AliExpress / eBay 等不同 schema 的数据包，处理成统一数据底座。

核心链路：

```text
合规数据提供商交付
  → ODS 原始层原样留存（可重跑）
  → 字段/币种/单位/类目同构
  → DWD StandardItem 明细
  → 去重 / 合规过滤 / 质量分级（A/B 上线，C 仅离线）
  → 线上检索库 + 向量库 + ADS 指标
  → ItemSearch / 三塔 / CategoryInsight / PriceCompare 消费
  → 线上 trace 回流 → ADS → 采买决策 + 训练飞轮
```

为什么这样：平台 ToS、反爬、schema 不稳；自建爬虫合规与稳定性风险高（原文对比表明确反对「直接爬平台页面」）。

### 8.2 业界真实存在的「可采买」形态（补强叙事，非原文点名厂商）

面试可以说「业界常见是买结构化商品数据 API / 数据集，而不是自己爬」——下列是**真实存在的商业产品类型**（举例，不是声称 Globex 一定用了哪一家）：

| 类型 | 真实例子（公开产品） | 典型拿到什么 |
|---|---|---|
| Amazon 结构化商品 API | [Rainforest API](https://www.rainforestapi.com/)（Traject Data） | 按 ASIN/搜索拿标题、价格、类目、变体等 JSON |
| 多市场数据集 / 采集 API | [Bright Data](https://brightdata.com/) 电商与 Amazon/eBay 等数据集产品 | 批量或 API 拉取公开商品字段 |
| eBay 实时商品流类 API | Traject 体系下的 Countdown 等（与 Rainforest 同生态常见） | eBay 侧结构化商品数据 |
| 官方开放平台（补充，不是 Globex 主路径） | eBay Browse API、Amazon SP-API（偏卖家/合作方） | 有授权场景可用；Globex 原文主路径仍是「采买提供商」 |

**自洽说法（推荐背这段）**：

> 我们不维护四套爬虫。商品主数据按品类/平台向合规数据提供商采购批次或调用其 Product Data API，落 ODS；工程侧做 StandardItem 同构和质检。价格/库存用更高频增量更新；主数据天级。Agent 运行时只打内部检索/向量服务，不直连亚马逊/虾皮网页。

### 8.3 除了商品库，还有哪些数据

| 数据 | 来源（原文/合理补强） |
|---|---|
| 品类知识卡片（RAG） | 由商品与运营内容抽取进 OpenSearch（第 13 / 13-1）；可含小模型抽取 + 入库门禁 |
| 用户长期偏好 | 会话 Reflect 写入 Store；不是爬来的 |
| Web 实时资料 | `WebSearch` 工具（评测/趋势）；与商品库分离 |
| 汇率 FX | 演示可用静态表；生产可用公开汇率 API 或内部财经服务（演示与生产要说清） |
| 关税/运费规则 | 业务配置表（`duty` / `shipping`）；跨境真实计税更复杂，文档级是可解释近似 |
| 训练/评测 | 人工+自动 Rubric、购买/点击日志、跨语言对齐对（第 04-2 / 08） |
| Trace 回流 | 线上 Agent 轨迹 → ETL → ADS（平台成功率、覆盖缺口）→ 指导下次采买哪些品类 |

### 8.4 学习/复刻阶段怎么「模拟」数据（诚实）

| 阶段 | 做法 | 面试怎么说 |
|---|---|---|
| 本地复刻 demo | 四平台静态 JSON/目录 mock | 「先验证 Agent 链与 Contract，数据是 deterministic mock」 |
| 次生产级叙事 | ODS←提供商 API/批次；DWD←同构；向量←Item 塔离线灌库 | 「生产按 09-1 采买，我负责的是同构/检索/Agent，不是爬虫」 |
| 禁止说成 | 「我们爬了 Amazon」 | 与原文明确冲突 |

5. 灰度：`app/ops/` + 可行性评估；声明是补丁。
