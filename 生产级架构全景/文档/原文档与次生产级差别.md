# 原文档与次生产级差别

> 日期：2026-08-09  
> 用途：分清「Globex 原文已经给了什么」和「为模拟次生产级灰度我们补了什么」，避免面试时把补丁说成原文、或把原文边界说成生产完备。  
> 配套阅读：同目录《次生产级灰度模拟可行性评估》

---

## 1. 一句话

| 层 | 来源 | 能否说「原文就是这样」 |
|---|---|---|
| Agent 业务内核（主/子 Agent、九工具、召回、压缩、记忆、评测方案） | `globex/` 原文档 | **能** |
| 灰度运营壳（flag、放量阶段、回滚矩阵、任务级四轴观测定义） | 本全景补丁 `app/ops/` + 业界惯例 | **不能**；必须说「原文未覆盖，我们按次生产级补齐讲解」 |
| 复刻工程取舍（如用 `create_agent` 替代弃用 API） | `globex-replica-docs` / `globex-agent` | **不能**当原文；只作「复刻现状」事实 |

## 2. 原文档明确「做到了什么」

### 2.1 端到端产品闭环（第 15 章）

- HTTP 启任务、WebSocket 推 AGUI、取消、上传/下载协议  
- 主 Agent 后台跑，立即返回 `thread_id`  
- 跨平台 fork + 合流比价精挑 + 清单展示  

原文自己说：这是「可交互业务链路」，**不是**完整生产化。

### 2.2 稳定性与局部降级（第 14、13-1 章）

| 原文有的 | 解决什么 |
|---|---|
| fork 深度 / 超时 / 循环检测 / 结果截断 | Agent 动态性失控 |
| 主 30 轮 + 300s、子更小轮次与超时 | 不收敛 vs 卡死 |
| OpenSearch / Reranker / Tower 失败兜底 | 召回链路可用性 |
| 空召回走 WebSearch | 冷启动 |
| 召回指标看板 + 偏离告警思路 | 召回侧可观测 |

这些属于「次生产级」里**原文已经给的工程肌肉**，讲稳定性时优先引用这里。

### 2.3 质量与训练闭环方案（第 08 章）

- P0 / P1 / P2 Rubric、Judge、高分轨迹 SFT、Agentic RL reward  
- 这是「质量轴」的原文答案  

差别在于：原文偏**训练与离线评测方案**，较少写成「灰度放量时的在线门禁与自动降流量」。

### 2.4 简历四条的机制与部分数字

| 点 | 原文 | 差别说明 |
|---|---|---|
| 主+fork 子 Agent、上下文隔离、并行 | 第 03 / 11 / 14 章 | 机制完整 |
| 30 轮 / 300s | 第 14 章精确常量 | 完整 |
| 并行降延迟约 65% | 串行≈和、并行≈最慢的量级描述 | 数字需自辩护测量口径 |
| Cache Breakpoint、命中率 15%→80%+ | 第 05 章 | 数字原文有 |
| 长期记忆、软衰减、黑名单优先 | 第 06 章 | 机制完整；**72% 原文未找到** |
| 三塔 + 双通道 + Hybrid / ANN | 第 04 / 11 章 | 机制完整；**+22% / +35% 原文未找到该对比** |

## 3. 原文档明确「没做 / 推后做」的

摘自第 15 章小结与各章边界：

| 类别 | 原文态度 |
|---|---|
| 鉴权、限流、多租户 | 第 15 章：本章不处理完整生产化问题 |
| 限额、容灾、观测、安全 | 第 15 章：上线前还需要补 |
| 完整 Redis/Postgres/OpenSearch 组合作为第一版门槛 | 复刻方案也列为非第一阶段目标；原文是分章演进 |
| 真实四平台授权同时接入 | 非轻量原型门槛 |
| SFT / Agentic RL 真正训起来 | 第 08 章给方案与骨架，不是「已上线训练平台」 |

**结论：原文是「可端到端演示 + 可演进到生产的设计说明书」，不是「灰度上线 runbook」。**

## 4. 次生产级相对原文多出来的东西（本全景补丁）

下列内容**不是** `globex/` 里的模块名或定稿目录，是为「模拟灰度上线」补的讲解层：

| 补丁 | 放哪里 | 为什么补 |
|---|---|---|
| 能力级 feature flag / kill switch | `app/ops/flags.py` | 部署与放量解耦；可单独关 fork / 三塔 / 压缩 / 记忆注入 |
| 四轴指标定义 | `app/ops/metrics.py` | AGUI ≠ 生产观测；需要任务级质量/延迟/成本/错误口径 |
| 回滚矩阵 | `app/ops/rollback.py` | 何种信号关哪些开关，避免「出问题再改代码」 |
| 灰度阶段故事线 | `app/ops/rollout.md` | 内部 → 小流量 → 升量/回滚的叙事落点 |
| 简历数字口径页（后续） | `文档/` | 尤其 72%、22%、35% 必须可辩护 |

面试时正确说法：

> 「业务上的主子 Agent、工具链、召回、压缩、记忆按 Globex 设计文档落地；灰度时的开关、放量、回滚和任务级观测，文档里没有单独成章，是我们按次生产级实践补的一层 ops。」

错误说法：

> 「原文第 X 章已经规定了 feature flag 和自动回滚矩阵。」——没有。

## 5. 容易混淆的三处「看起来像生产、其实不是同一层」

### 5.1 AGUI 事件 ≠ 生产观测

- **原文**：WebSocket 推 `tool_start` / `fork` / `task_result` 给前端看过程。  
- **次生产级还要**：任务成功率、超时率、token 成本、缓存命中、P0 失败率等**可告警、可进回滚阈值**的指标。  
- 关系：AGUI 是体验层；`ops/metrics` 是运营层。可以共用 trace，但职责不同。

### 5.2 Rubric/Judge ≠ 灰度自动降流量

- **原文**：离线/训练向的自动打分与数据飞轮。  
- **次生产级还要**：固定回归集卡发版 + 灰度抽样质量门槛 + 跌破阈值则减流量或关 flag。  
- 关系：Judge 是评分器；放量门禁是运营策略，原文没写成完整策略表。

### 5.3 召回侧降级 ≠ 全链路灰度 kill switch

- **原文**：OpenSearch/Reranker/Tower 失败时的工具内兜底，保证主 loop 仍拿到低置信结构。  
- **次生产级还要**：整能力开关（例如全局关闭并行 fork、回退串行；关闭三塔改关键词）与流量百分比。  
- 关系：一个是**组件降级**，一个是**放量控制**。

## 6. 目录归属速查

| 你看到的路径 | 算原文还是补丁 |
|---|---|
| `app/agent/`、`app/tools/`、`app/api/`、`app/recall/`、`app/memory/`、`app/compress/`、`app/eval/`（方案级） | **原文**（以 `globex/` 对应章节为准） |
| `app/ops/` | **次生产级补丁** |
| `demos/` | 学习验证脚本，非正式工程 |
| `文档/` | 讨论与终稿，非正式工程 |
| `globex-agent/` | 复刻代码现状，可能落后于全景目标架构 |
| `globex-replica-docs/` | 我们自己的复刻计划，**不作为原文依据** |

唯一需要特别说明的原文内部矛盾：第 05 章早期用 `app/context/` 细拆，第 14 章定稿用 `app/compress/`。全景跟定稿；这是原文版本演进，不是我们发明的架构。

## 7. 使用纪律

1. 讲机制、讲简历四条内核 → 只引 `globex/`，并尽量落到章与行。  
2. 讲灰度放量、开关、回滚、四轴观测 → 引 `app/ops/` 与本文，并声明是补丁。  
3. 讲「我们复刻做到哪了」→ 引 `globex-agent/`，不要说成生产现状。  
4. 数字说不出出处 → 标「自拟可辩护口径」或「待补测」，不要谎称原文数字。
