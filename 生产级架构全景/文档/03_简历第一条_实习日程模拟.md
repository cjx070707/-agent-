| 块 | 学什么（大白话） | 面试用来干嘛 |

### 第 1 天：先搞懂整条链，别急着写 fork

**大白话**  
导师（模拟）：「先别写并行。你能不能讲清楚：用户一句话进来，不 fork 的时候，主 Agent 怎么走到 Summary？」

**你做什么**

- 标出：**哪些绝对不该 fork**（比价、运费）。

**核心代码落点**

**坑与解决**

### 第 2 天：同质 fork 是什么（概念钉死）

**大白话**  
「子 Agent 不是搜索小弟，是主 Agent 的克隆，只是换了个房间（thread）干活。」

**你做什么**

- 对照表：同模型、同 Prompt、同工具；不同 `thread_id` / checkpoint。

**核心代码落点**  
- 先只看 `dispatch_tool` 的 docstring（适用场景）和返回值是 `str`。

**坑与解决**  
| 坑 | 解决 |
|---|---|
| 说成「搜索 Agent / 比价 Agent」异构分工 | 改口：多平台是同质任务，所以克隆自己 |
| 说「子 Agent 返回结构化参数」 | 改口：返回字符串 Observation，尽量约定 JSON |

**怎么验**  
用自己的话讲 2 分钟「同质 vs 异构」；录音对照 `01` 禁忌。

### 第 3 天：写出 / 吃透 `dispatch_tool`（本条核心）

**大白话**  
今天就一件事：主 Agent 怎么「派人」。派人 = 调 `dispatch_tool`，里面再跑一个子 Agent。

**你要对着看的核心逻辑（理解用）**

```text
dispatch_tool(demands):
  enter_fork()                    # 深度+1，太深就拒绝
  延迟 import build_agent()       # 避免循环依赖
  sub_thread_id = sub-xxx
  子 Agent.invoke(demands, thread_id=sub, 轮次上限更小)
  return 最后一条消息的字符串
```

文件：`app/agent/dispatch_tool.py`、`fork_guard.py`（先配合看深度）。

**坑与解决**  
| 坑 | 解决 |
|---|---|
| 文件顶部互相 import 炸了 | `build_agent` 放到函数里面再 import（延迟导入） |
| 以为一个 dispatch 里就会并行四平台 | 一个 dispatch = 一路子任务；并行 = 主模型**一轮喊多个** dispatch |
| 子任务把主对话污染了 | 检查是否用了新的 `sub-*` thread_id |

**怎么验**  
能指着流程说：demands 进、字符串出、thread 不同、超深返回拒绝文案而不是进程崩溃。

**建议测试意图（断言级）**  
- 超深度 → 返回带「拒绝」的字符串，不抛到外面把主 loop 打死。  
- 子 thread_id 前缀是 `sub-`。

### 第 4 天：Prompt——让模型愿意、且正确地 fork

**大白话**  
代码只提供「能派人」的工具；**肯不肯派、怎么派**，很大程度靠 system prompt。

**你调 Prompt 时写什么（要点，不是背全文）**  
1. 多平台检索：优先一轮多个 `dispatch_tool`，每个平台一路。  
2. 比价/运费：自己调工具，不要 fork。  
3. 子任务 demands 里写清平台、预算、材质等约束。  
4. 子任务输出尽量紧凑 JSON（platform、candidates…）。  
5. 若返回「拒绝/超时」：换思路，别死磕同一派法。  
6. `shopping_summary` 之后别再开检索。

落点：`app/prompt/prompts.yml` + `prompts.py`。

**坑与解决**  
| 坑 | 解决 |
|---|---|
| Prompt 写了「可以并行」，模型仍串行 | 加更硬的规则 + 一例 few-shot；验收看轨迹里同轮是否多个 dispatch，而不是只看总耗时 |
| 子 Agent 回散文，主 Agent 合流挂了 | 收紧输出 schema；解析失败就降级重试或当失败进回归 |

**怎么验**  
列出你改的 3 条 Prompt 规则，并说明每条防的是哪种蠢行为。

### 第 5 天：防失控——深度 / 循环 / 截断

**大白话**  
「模型会傻、会贪、会递归。」生产级先假设它会作恶，再用工程刹住。

**核心代码落点**  
- `fork_guard.py`：深度上限（如 2）  
- `middleware.py`：同工具别刷太多次；结果太长截断  
- `main_agent.py`：主 30 轮；子更小轮次  

**坑与解决**  
| 坑 | 解决 |
|---|---|
| 只做了 30 轮觉得够了 | 补：深度、超时、循环、截断——面试说「纵深防御」 |
| 并发下深度计数全变成 0 | ContextVar 必须配合会复制 context 的执行器（见 demos） |
| 截断太狠丢关键字段 | 截断同时提示「缩 top_k / 缩窄 query」 |

**怎么验**  
口述四件套各防哪种故障；跑 `demos/demo_parallel_fork.py` 的 ContextVar 部分（可选）。

**建议测试意图**  
- 深度 3 → 拒绝。  
- 同工具超限 → 拦截且 run 可继续。  
- 超长 tool 结果 → 长度被砍并带提示。

### 第 6 天：300s 超时 vs 并行（对齐第3档，不深挖重构）

**大白话**  
今天搞懂一句话：**变快靠并行；停得住靠超时真取消（目标第3档）。**

**你做什么**  
- 读 `02_同步_并发_异步定稿.md`。  
- 看 `demos/demo_timeout_guard.py`：线程池「不等了」≠ 协程被取消。  
- 面试话术背下来：目标 `wait_for(ainvoke)`；65% 不是 async 带来的。

**坑与解决**  
| 坑 | 解决 |
|---|---|
| 把异步和 65% 绑一起 | 拆开说：并行=多路同时跑；异步=网关+真取消 |
| 觉得必须先全仓改 async 才能写简历 | 定稿已说：学习优先级并行 ≫ 异步口述 |

**怎么验**  
30 秒说清第3档目标；再 30 秒说清 65% 测量直觉。

### 第 7 天：并行收益——你「测过」65%

**大白话**  
导师：「别空口快。给我串行 vs 并行的数。」

**你做什么（模拟一次正经对比）**  
1. 固定 query（多平台旅行三件套类）。  
2. 组 A：尽量串行（不允许同轮多 dispatch / 或叙事上关并行）。  
3. 组 B：允许同轮多 dispatch。  
4. 各跑多次，记墙钟；**同时看轨迹**：B 组是否真出现 ≥2 个并行 dispatch（没有则数据作废）。  
5. 本地理解公式：跑 `demos/demo_parallel_fork.py`（sleep 模拟 I/O → 约 66.7%）。

**坑与解决**  
| 坑 | 解决 |
|---|---|
| 只比总时间、没看是否真并行 | 轨迹里数同轮 dispatch 个数 |
| 模型不扇出 | 先修 Prompt；汇报时诚实写「扇出率」 |
| 并行更快但更费钱 | 面试主动提：多份子 Agent 前缀，延迟收益 vs token 成本 |

**怎么验**  
能讲：对比怎么设计、无效数据怎么剔、65% 量级从哪来。

### 第 8 天：合流稳定性 + 灰度一句话

**大白话**  
子 Agent 回了垃圾字符串 → 主 Agent 比价吃瘪。灰度时并行出问题 → 先关开关，不先改核心逻辑。

**你做什么**  
- Prompt：子输出 schema；主侧解析失败怎么降级（重试 / 记失败）。  
- 看一眼 `app/ops/flags.py`、`rollback.py`：`ENABLE_FORK_PARALLEL` 关了会怎样。  
- 准备回归：2 条「应多平台 fork」、1 条「闲聊走 ChatFallback」、1 条「单平台不必硬 fork」。

**坑与解决**  
| 坑 | 解决 |
|---|---|
| 当类型系统保证了子输出 | 承认是 Prompt 契约，用评测盯「可解析率」 |
| 出事就改 Agent 逻辑 | 先拨 flag 降级串行，再排期修 |

**怎么验**  
口述一次「线上合流翻车我怎么查轨迹、怎么回滚」。
