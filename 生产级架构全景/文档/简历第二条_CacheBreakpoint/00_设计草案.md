## 1. 这条在讲什么（一句话）

长对话 / 长 Agent 任务里，**上下文会只增不减**；乱压缩会把 Prompt Cache 打穿。  
Cache Breakpoint = 画一条「盖章线」：**线前一字不动保缓存，线后才允许摘要/截断**，在省 token 和保命中率之间取平衡。

---

## 2. 和第一条的关系（别学成两张皮）

| | 简历① 多 Agent | 简历② Cache Breakpoint |
|---|---|---|
| 痛点 | 单 Agent 上下文爆炸、串行慢 | 主线多轮后 token/延迟/质量失控 |
| 手段 | fork 把脏活隔离子上下文 | 主（及长）会话内分层压缩 |
| 互补 | 子 Agent 只回短结果，少往主线灌 | 主线仍会变长，靠断点治理 |
| 数字 | ~65% 延迟 | 命中 15%→80%+；综合成本约 -35%（原文表） |

面试金句：fork 是「别把垃圾倒进主房间」；Breakpoint 是「主房间堆满了怎么收拾还不拆掉可复用的前缀」。

## 3. 必须钉死的核心机制（原文 05）

### 3.1 冲突

- Prompt Cache：前缀**完全一致**才命中；改一个空格都可能 miss。  
- 盲目摘要：前缀天天变 → 命中率从很高掉到很低 → **更贵**（原文：盲目压缩命中约 15%，Cache-Aware 约 80%）。

### 3.2 断点怎么定

- 把断点锚在「最近 K 个工具调用」的起点（常见 `keep_recent=3`）。  
- **最近 K 轮最不稳定 → 放断点之后可压缩**；不是「最近最珍贵所以缓存」。  
- 断点之前：system / 稳定历史 **一字不动** + 打 `cache_control`（厂商相关）。  
- 断点之后：可截断、摘要；当前用户追问通常不缓存。

### 3.3 不止断点一层（原文五层治理，学习可抓主次）

| 层 | 大白话 | 学习深度建议 |
|---|---|---|
| L0 工具侧控体积 | 工具少返回、字段精简、长度截断（①里 middleware 已沾边） | ★★ 必懂 |
| L1/L2 断点 + 压缩 | compute_breakpoint + compress 断点后 | ★★★ 本条核心 |
| Context Manager | 每轮按需重建最小上下文 | ★★ 能讲清 |
| 厂商 cache_control | Anthropic 等显式断点；也有自动前缀缓存的厂商 | ★ 知差异 |
| 与 Store 边界 | Store=跨会话偏好；Breakpoint=会话内 token | ★★ 必分清 |

### 3.4 原文内部一处要对齐的矛盾（设计时写死）

- **05 最终 Q&A**：断点**之前**稳定不改；压缩发生在断点**之后**。  
- **14 章示例代码**有一段像是在压缩 `messages[:breakpoint]`（断点前）——与 05 定稿冲突。  

**本全景定稿建议：以 05 Q&A 为准——只压缩断点之后；断点前绝对不改。**  
写学习稿 / 升级 `app/compress/*` 讲解时按此执行，并在文中点明「不跟 14 章那处示例笔误走」。

### 3.5 简历数字口径（可辩护）

| 简历说法 | 原文支撑 | 自学怎么验 |
|---|---|---|
| 命中率稳住约 80% | 05 表：Cache-Aware ≈80%；另有 15%→80%+ | 讲清「前缀不变」；有条件看 cache_read vs cache_creation |
| 10+ 轮不超约 30k | 05 痛点里多轮膨胀到 2 万+；工具一次可吃 3 万 | 讲「断点后摘要 + L0 截断」组合；30k 当目标水位 |
| 综合成本约降 35% | 05 口径原文有 | 与命中率一起说，别只报压缩率 |

评估不能只看 token：还要看任务成功率、**约束遗漏**（别摘要掉「不要塑料」）、恢复能力（thread/checkpoint）。

## 5. 学习与实习模拟怎么设计（草案）

### 5.1 知识地图

| 学什么 | 为什么 |
|---|---|
| Prompt Cache 前缀匹配 | 否则讲不清为何不能乱摘要 |
| Breakpoint 定位（keep_recent=K） | 本条算法核心 |
| 断点后压缩 vs 断点前不动 | 与盲目压缩对比 |
| 挂到主 loop 的时机（每步后 / post hook） | 和①的 AgentLoop 接上 |
| L0 工具截断 | 性价比最高的第一道防线 |
| 和长期记忆 Store 的边界 | 防面试搅成一锅 |
| 观测：命中率、约束遗漏、任务成功 | 数字怎么守 |

厂商细节（Anthropic `cache_control` vs OpenAI 自动前缀）：**知差异即可**，次生产级叙事用「稳定前缀 + 显式/隐式缓存」概括。

### 5.2 实习日程粒度（沿用①确认过的风格）

大白话「天」+ 核心代码落点 + 坑与解决 + 怎么验。建议压缩为 **6～7 天**，例如：

1. 痛点：不压缩会怎样；盲目压缩为何更亏  
2. 断点规则：画盖章线；keep_recent  
3. `compute_breakpoint` 吃透 + 小 demo  
4. 断点后压缩：保什么字段（预算/材质）防约束遗漏

6. 指标与「80%/30k」口径；和 Store 分界

### 5.3 典型坑（预埋进日程）

| 坑 | 解决方向 |

## 6. 次生产级说法（预填，待你点头）

- **机制跟原文 05**（断点前不动、断点后压）。  
- **接入叙事跟 14**：主 loop 步骤后触发压缩；目标形态仍在第3档异步链上，但本条不要求先练整仓 async。  
- **灰度**：可增加概念开关 `ENABLE_CACHE_BREAKPOINT`（ops 补丁）；命中暴跌或约束遗漏升高 → 临时关压缩或减小激进摘要。  
- **不假装**：不必真接 Anthropic 账单；用「前缀是否被改写」+ 原文表做口径。
